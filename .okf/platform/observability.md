# The tier

Four workloads and a config bundle, chained by capability back to [Garage](/platform/storage.md) — see the [capability graph](/architecture/capability-graph.md):

```
garage → loki → alloy
kube-prometheus-stack → gotify
kube-prometheus-stack → traefik-observability-config
```

- **kube-prometheus-stack** — Prometheus, Alertmanager and Grafana. Grafana authenticates against [kanidm](/platform/identity-kanidm.md); the Prometheus and Alertmanager UIs are served from the tailnet while Grafana takes the country whitelist, which is why this bundle still installs a middleware set.
- **loki** — `SimpleScalable`, chunks and indexes in Garage over the in-cluster endpoint, `s3ForcePathStyle: true`. Grafana and Alloy both address it through `loki-gateway`, because the split targets put the ruler on `loki-backend`: a `loki-read` URL serves every query path and so looks correct, but 404s the alerting page's `/prometheus/api/v1/rules`. The chart comes from `grafana-community.github.io` — the OSS lineage, forked at 6.55.0; the `loki` chart still on `grafana.github.io` is Grafana-Enterprise-Logs-only from 7.x, so never point the HelmRepo or renovate back there. `monitoring` carries the whole mixin — one ServiceMonitor, the recording rules, the alerts and the dashboards.
- **alloy** — the log shipper, scraped for the pipeline's own metrics.
- **traefik-observability-config** — traefik's ServiceMonitor, which cannot live with traefik; see the note below.
- **gotify** — the notification sink. It authenticates against [kanidm](/platform/identity-kanidm.md) natively, with local password auth left on as break-glass.

# Log pipeline

`cue/infrastructure/observability/alloy/files/config.alloy` is a `#ConfigMapFiles` source, not a chart value. It discovers pods via `discovery.kubernetes` (role `pod`), relabels `__meta_kubernetes_*` into `namespace`, `pod`, `container`, `node` and `app` (from `app.kubernetes.io/name`), derives `job` as `<namespace>/<container>`, and writes to `loki-gateway.loki.svc.cluster.local`. Which Alloy construct sets each kind is [upstream behaviour](/reference/loki-stream-labels.md); the set it produces is [the telemetry label convention](/platform/telemetry-labels.md)'s five, which `loki.process.common` settles for every branch at once — `pod` and `node` are demoted there to structured metadata, and `instance`, which the `loki.source.*` components add rather than any rule, is dropped. `stage.structured_metadata` **moves** a label out of the set rather than copying it, which is why the demotion needs no `label_drop`, and it skips a branch carrying neither rather than stamping empty values.

**One stream is exempt from the `pod` demotion**, which is why that stage sits inside a `stage.match` on `job!="loki/canary"`. `lokiCanary.push` is off, so the canary writes to stdout rather than pushing at the gateway and Alloy is inside the loop it measures — collection as well as write and query. It then reads its own lines back with `{<streamname>="<streamvalue>", <labelname>="<pod>"}`: the stream pair defaults to `stream="stdout"`, a label Alloy never sets, so `extraArgs` points it at `job="loki/canary"`; `labelname` chooses the other label's name but its value is hardcoded to the pod name, so no other label can carry it. That stream also carries the canary's stderr, because the Kubernetes log API merges both streams and upstream's `stream="stdout"` default is what normally excludes it; each diagnostic then fails the reader's probe parse and is re-reported on stderr, a loop that took the stream from ~150 KB to ~300 MB per pod per 5 minutes. `loki.process.common` therefore drops every canary line that is not a probe. A demoted `pod` there is not a slow query but a canary reporting every line missing, forever. Four pods, four streams, and the `label-conformance` dashboard's out-of-convention panel reports them as the one legitimate entry it has.

Two sources feed one `loki.write.default`: those pod logs, and cluster events through `loki.source.kubernetes_events` (`job_name` `kubernetes/events`, JSON). Both stamp a static `cluster: nyx`.

**Both sources need the clustering ring, and it takes two halves.** Alloy is a DaemonSet and `discovery.kubernetes` carries no node filter, so every replica sees every pod. `loki.source.kubernetes` shards targets across peers only when the component's `clustering` block is on _and_ `alloy.clustering.enabled` is set, which is what builds the `alloy-cluster` headless Service the chart's `--cluster.join-addresses` names; either half alone is inert. With the ring off, four replicas shipped identical lines and nothing downstream showed it — Loki silently drops an exact duplicate of `(timestamp, line)` within a stream, and the pod branch labels `node` from the target rather than the shipper, so the four copies land in one stream. `loki.source.kubernetes_events` shards per namespace and `namespaces` is empty, so all replicas hold the same all-namespaces target and the ring is the only thing electing a single collector. The tell is `loki_write_sent_entries_total`, near-equal across all four pods.

# Per-workload pipelines

**Configure the app before parsing it.** Two questions come before a pipeline is written: can the workload emit a structured format, and can it filter by level or module at the source? A structured mode replaces a regex over a human format with a `stage.json`; a source-side level directive is strictly cheaper than a `stage.drop`, which pays transport and Alloy CPU before discarding the line. Neither is free — a level directive is coarser than a named-message drop, taking the module's other messages with it, and both need a restart where an Alloy edit reloads. garage is the worked example; most of the fleet exposes no such knob and parses a console format.

**Every pipeline promotes `level` and little else**, against [the admission test](/platform/telemetry-labels.md). It is the field whose consumer cannot read a line — the logs dashboard's level picker — where that same dashboard searches everything else with `|=`. Two more pass the test for their own reasons: `target` on garage, because `stage.output` discards the JSON envelope carrying it, and `caller` on klog, where `sum by (caller)` is the diagnostic.

**A workload's log handling lives in its own package.** `alloy run` is pointed at a directory rather than a file, and alloy loads every `*.alloy` in it (no recursion) as **one graph**, so a file dropped in beside the base config is live config that can reference the base's components by name. `#AlloyPipeline` renders one into a ConfigMap in the workload's own namespace; a `kiwigrid/k8s-sidecar` pair in the alloy pod — `METHOD=LIST` as an init container so the base is on disk before alloy starts, `METHOD=WATCH` alongside it to reload on change — collects every ConfigMap labelled `alloy_config` from every namespace into `/etc/alloy.d`. Alloy's ClusterRole already grants cluster-wide `configmaps` get/list/watch and a sidecar shares the pod ServiceAccount, so this needs no RBAC of its own. servarr is the worked example.

The base keeps the parts that are genuinely shared: `discovery.relabel.k8s_pod_logs` holds the standard label rules, which a workload file narrows rather than repeats, and `loki.process.common` is the single place `cluster` is stamped. Which pods a workload claims is a **label, not a name in the base config** — `logs.vonarx.online/pipeline` — so the generic branch keeps only pods where it is empty and alloy never learns what workloads exist. `#AlloyPipeline` emits that label and the ConfigMap key from one `app` field, which is also what stops two workloads writing the same filename into the shared directory.

**One bad file stops the whole fleet's logs.** The graph is all-or-nothing: a dangling reference in any file fails the load. A reload survives it — alloy keeps the last good config — but a pod restart crashloops, so the failure surfaces later than the edit that caused it. `checks.alloyValidate` assembles the same union the sidecar delivers and rejects it before it can reach a node; that check is what makes this layout safe, not a convenience. Component labels are a second namespace it guards — `#AlloyPipeline` makes filenames unique but two workloads can still declare the same `loki.process "logs"`.

The claim label is the destructive half: a pod carrying it leaves the generic branch whether or not anything picked it up, so a pipeline that fails to load loses that workload's logs rather than falling back. **Accepted, not overlooked.** Inverting it — base keeps everything, workload files drop what they duplicate — costs double API tailing on every claimed pod forever to cover a window only an edit can open, and these files change only when an app changes its log format. Verify a new pipeline loaded when you add one; that is the whole mitigation. Migrating a workload also double-ships its lines once, in the window where both branches still hold the pod, and Loki does not collapse the pair — the per-app expression strips the trailing newline with `\s*$` and the generic branch does not, so the copies differ by a byte and the exact-duplicate drop misses them. It clears on the next relabel evaluation.

`alloy.configMap.key` is `../alloy.d`. The chart interpolates it into `run /etc/alloy/<key>` and hardcodes the config volume as a ConfigMap, so escaping the directory is the only way to point `run` at a path a sidecar can write; the ConfigMap stays mounted at `/etc/alloy` where nothing reads it. A post-render patch is the obvious alternative and is worse — the arg is addressable only by index, so a chart that inserts a flag ahead of it rewrites the wrong one silently. The real fix is upstream and unmerged: [alloy#1176](https://github.com/grafana/alloy/issues/1176), open since 2024. `configReloader` is off — it watches `/etc/alloy`, which alloy no longer reads.

# Log levels

**Every `stage.regex` here wants `(?s)` and a `\s*$` tail.** Lines arrive with a trailing newline and RE2's `$` matches only end-of-text — unlike Perl it does not match before a final newline — so `.+$` never reaches its anchor, and a `stage.regex` that matches nothing is silent: no captures, no error. The defect survives as long as the captures are unused and surfaces the moment a `stage.structured_metadata` is added for them to feed. That same silence is useful: a miss leaves the extracted map untouched, so an **optional** field belongs in a second pass over `message` rather than an optional group, which writes the empty string and stamps it on every line that lacks the field. Fixed widths are the related trap — kanidm's tracing-forest output pads the level out to a column and indents children past it, so only `\s+` fits every depth. `stage.template` inverts that silence: it **creates** its `source` field when the field is absent, so it still runs after a regex that missed — a chain of `else if` therefore needs a final `else`, or the fallthrough branch stamps its severity on every line the regex could not parse.

**kanidm's records are span trees, not lines.** `stage.multiline` folds every line sharing a kopid into one entry — tracing-forest buffers a tree and writes it on span close, so they are always contiguous — with roots identified by carrying no box-drawing glyph where children do; the negated class has to exclude the pad space as well, or ` +` gives one back, every child reads as a root and nothing folds. Its `detected_level` is therefore the **worst level in the request**, not the level of a line. Leave `max_lines` at its default: `max_line_size` is 256KB with `max_line_size_truncate` off, so an oversized record is discarded rather than trimmed.

**Two pipelines belong to no workload package** and ship beside the base config instead: `events.alloy`, which parses the cluster-events source `config.alloy` declares, and `klog.alloy`, keyed on a log format. klog — what `k8s.io/klog/v2` emits, and so most of the Kubernetes ecosystem — comes from six containers across four charts, a set that grows whenever a chart adds a sidecar and whose largest member, snapshot-controller, is a raw upstream Kustomization with no values to hang a claim label on. `klog.alloy` selects with a line filter inside a `stage.match` selector instead of a pod label. The stream selector has to name a label that exists at that point in the graph — `namespace` does; `cluster` does not, being stamped downstream in `loki.process.common`. It extracts `caller` (`leaderelection.go:267`), the call site `sum by (caller)` groups on to find what is flooding, and its drop names the three steady-state lease messages one by one rather than the caller, so that acquiring a lease, losing one or failing to renew one still arrives. **Multiline cannot work inside a content-matched block**: a stack-trace continuation carries no header, so it never matches the filter and never enters the block to be folded.

**gotify is zerolog's console writer, and its own health suppression never fires.** The shape is `<RFC3339> <LVL> <message> <k=v…>` over the three-letter vocabulary `TRC DBG INF WRN ERR FTL PNC`, plus `???` for a nil level; colour cannot appear, because gotify takes `NoColor` from `!isatty(stdout)` and a container's stdout is a pipe. gotify skips logging `/health` only when the client address is loopback, and the kubelet probes from the node, so 94% of its output was one repeated line. Fields are emitted **alphabetically**, not in the order the code adds them, which is what puts `path` next to `status` and lets the drop name `path=/health status=200` — keeping a probe that starts failing.

**garage is configured rather than parsed.** `GARAGE_LOG_FORMAT=json` and `RUST_LOG` reach it through the chart's `environment` list, and between them they remove most of the work: tracing-subscriber's JSON mode yields `level`, `target` and `message` as fields — so no regex, and no `(?s)` or `\s*$` tail, the trailing newline falling outside the JSON string — while `garage_block::resync=warn,garage_table::gc=warn` stops the steady-state block-delete and GC-success chatter, 84% of the workload's volume, from being emitted at all. Setting `RUST_LOG` replaces garage's own default outright, so `netapp=info,garage=info` has to be restated beside the additions; EnvFilter matches a target by prefix and the most specific directive wins, which is how a single `garage=info` ever covered every `garage_*` crate. The pipeline promotes `level` and `target` and nothing else: a `stage.output` makes the stored line the message rather than the envelope, which destroys those two and leaves every request-log field — client, access key, method, path, error status — in the line where a filter expression reaches it. ANSI would otherwise have been the first problem: colour is gated on `NO_COLOR` alone with no tty check, so every line in a pipe carries escape sequences.

**jellyfin is Serilog's console writer, and Loki cannot read its level.** The `u3` vocabulary — `VRB DBG INF WRN ERR FTL` — is not in `discover_log_levels`' heuristic, so 99.6% of the workload reached Loki as `unknown`. `{NewLine}{Exception}` puts .NET stack traces on their own lines and ffmpeg's stderr passes through unwrapped, so the multiline anchor is the timestamp shape rather than a bare `[`: ffmpeg opens with one too (`[matroska,webm @ 0x…]`) and would read as a new record. The regex stops at the level for the same reason the fold exists: **a negated class crosses a newline**, so any capture reaching past it reads into the stack trace. <!-- cSpell:ignore Serilog matroska -->

**The loki gateway is configured quiet, not parsed.** Its nginx access log was the largest log source in the cluster — a third of everything nyx shipped, and all of it 2xx probes, canary traffic and Alloy's own pushes — because the chart defaults `gateway.verboseLogging` to on. Off, the chart wraps `access_log` in `if=$loggable` and only non-2xx/3xx survives, which is a handful of lines a day; nothing is lost, because Loki logs its own requests in logfmt with the query, byte counts and cache statistics attached. The survivors carry a `level` computed by an nginx `map $status` and reach Loki as JSON, so **Loki's own distributor classifies them** — `DefaultAllowedLevelFields` starts with `level` — and no Alloy pipeline exists for this workload at all. Two constraints hold that together: the format has to stay named `main`, because the chart hardcodes `access_log … main`, and `$upstream_status` has to be quoted, because it is empty when no upstream was reached and an unquoted empty value is not JSON.

**Cluster events carry their severity in a field, and the heuristic invents one instead.** `type` is `Normal` or `Warning` and nothing else, so `events.alloy` maps it — the two values are already the lowercase the convention below wants. Left to `discover_log_levels`, every Normal event read as `unknown`, Warning split arbitrarily between `warn` and `error`, and longhorn's `Removed unknown replica … in mode ERR from engine` — a Normal event — reached Loki as `error`, because the heuristic reads severity out of message text. The line stays the source's JSON, so LogQL's own `json` parser reaches every other field at query time and none of them are promoted. Its drop is one field rather than klog's composite: `ArtifactUpToDate`, `ReconciliationSucceeded` and `GitOperationSucceeded` were 95% of the stream and no Flux controller has a failure path that reports them, so the reason alone is the whole condition.

**A `level` that reaches Loki has to be lowercase.** `discover_log_levels` prefers the field over its own heuristic and copies the case it is given, and the [logs dashboard](/platform/observability.md) matches `detected_level` against a hardcoded lowercase list with `=~`, which is case-sensitive — so an `Info` is a line the dashboard silently cannot see. A `stage.template` with `ToLower` between the regex and the structured-metadata stage is what keeps a workload inside that convention.

Everywhere else the log level is Loki's own — `detected_level` structured metadata, from `discover_log_levels`, which nothing here disables. It is uniform across every namespace, at the price of being a heuristic: `unknown` still covers about a sixth of the volume, over half of that the `loki-canary` probe stream, which has no level to find. Structured metadata is invisible to the label API (`label_values(detected_level)` is empty), so a level picker has to carry a hardcoded list.

Two gates cover these files, failing for different reasons. `alloy fmt -w` runs in pre-commit beside `cue-fmt`, so formatting is canonical and auto-fixed rather than matched by eye — it loops because `alloy fmt` takes at most one file and pre-commit passes the batch. `checks.alloyValidate` owns semantics: it assembles the same union the sidecar delivers and rejects a dangling cross-file reference before it can reach a node. It parses stage templates too — an unknown function or a missing `{{ end }}` fails there rather than at runtime.

# Alerting path

Alertmanager → `gotify-alertmanager-bridge` (`ghcr.io/druggeri/alertmanager_gotify_bridge`) <!-- cSpell:ignore druggeri --> → Gotify.

The route tree is the chart's: naming `route.routes` replaces the default list wholesale, so Watchdog — the heartbeat that must never stop firing — has to be re-declared to `null` beside any addition.

The bridge chooses its Gotify application from a `?token=` on the webhook URL, so the receiver's URL is a credential and is not written in the release. It sets `url_file` instead, against a SOPS Secret named in `alertmanagerSpec.secrets`, which the operator mounts at `/etc/alertmanager/secrets/<name>/`. prometheus-operator re-marshals the raw config through its own structs and silently drops what it does not model: it does model `url_file`, but strips it below Alertmanager 0.26.0 and discards it outright when `url` is set alongside. Alertmanager reads the file inside each notification rather than at config load, so rotating the Secret needs no restart. The bridge's own `GOTIFY_TOKEN` is only the fallback for a request that carries no `?token=`; it holds a literal placeholder because the bridge exits 1 when it is unset, not because anything reads it. **The bridge rejects an alert with no `description` annotation** (`400 Missing annotation: description`), and the undelivered notification fires `AlertmanagerFailedToSendAlerts` on top — so every rule written here carries `description`, not just `summary`.

Gotify itself runs upstream's own `ghcr.io/gotify/server`, which puts its version under renovate's no-comment image manager — see [images and CI](/workflows/images-and-ci.md). Gotify keeps state in its own CNPG cluster and uses `ghcr.io/joker9944/postgresql-client`, another repo-built image, as a helper container.

**v3 configures from the environment only, and a list value is one bare CSV line.** The v2 `[a,b]` form still parses — as a single element with the brackets in it. That is silent both ways: gin discards the error from `SetTrustedProxies`, so a bracketed CIDR just leaves `X-Forwarded-For` unread, and CORS origins are unanchored regexes, where `[gotify.vonarx.online]` is a character class that matches almost any origin.

**A setting is disabled by an empty value, not an absent one.** gotify reads with `os.LookupEnv`, so a present-but-empty variable overrides a default where deleting the variable restores it — and several of those defaults are paths relative to the image's workdir. `GOTIFY_PLUGINSDIR` is the one that bites: gotify `MkdirAll`s a non-empty plugins dir and exits 1 when it cannot, so leaving it unset on a read-only root crashloops the pod against a default of `data/plugins`. Hence `null` in the release, which app-template renders as a present variable carrying a null value.

# Coverage gaps

**`ttlSecondsAfterFinished` below 15 minutes makes a CronJob's failures unalertable.** `KubeJobFailed` holds `for: 15m` against `kube_job_failed`, which kube-state-metrics stops exporting the moment the Job object is collected — so a `ttlSecondsAfterFinished: 120` deletes the evidence about thirteen minutes before the alert could fire. recyclarr's daily sync failed every run for two months behind exactly that gap, with `failedJobsHistory: 3` retaining nothing because the TTL outranks it. A short TTL is a deliberate trade for a job whose outcome is checked some other way; it is not a default to carry.

**`NodeMemoryHighUtilization` is a local rule, not the chart's.** Linux does not count the ZFS ARC in `MemAvailable`, and [mother](/platform/cluster-nyx.md) holds ~54 of its 62 GiB there, so the stock expression reads 95% on a host that is 11% used; the replacement adds back ARC above `arc_c_min` and contributes 0 where there is no ARC, so one rule still covers the fleet. `defaultRules` reaches `for` and `severity` per rule but never the expression, so a wrong default can only be disabled and re-declared — `defaultRules.disabled` alongside `additionalPrometheusRulesMap`, whose PrometheusRule carries the `release` label the default `ruleSelector` wants and a hand-written one would not. The node-exporter-mixin dashboards read `MemAvailable` directly, so they still show that node near 95% and disagree with the alert. That divergence is accepted — they are chart-rendered with no per-dashboard toggle, and correcting them means owning a replacement node dashboard.

**The chart's selector defaults narrow Prometheus to its own release, and a stray ServiceMonitor is silently never scraped.** `serviceMonitorSelectorNilUsesHelmValues` and its podMonitor/probe/rule/scrapeConfig siblings default to `true`, which compiles an unset selector into `release: kube-prometheus-stack` — a label no workload outside the chart carries. garage and opencloud both shipped a ServiceMonitor that matched nothing, for weeks, with no error anywhere: a selector that excludes a monitor is indistinguishable from no monitor existing. All five are now `false`, so any monitor in any namespace is picked up and a new one needs no magic label — garage and opencloud began reporting the moment that landed. `/api/v1/targets` is the only thing that answers whether a monitor is live; the CR's `serviceMonitorSelector` is what to read when it is not. What a monitor that is live then puts on each sample — `job` from the Service name, the operator's standard target labels, and what happens when the exposition carries one of them already — is [upstream behaviour](/reference/prometheus-metric-labels.md). Note that `additionalPrometheusRulesMap` still carries the `release` label deliberately — see below.

Traefik is the third app-level monitor, and it is the one that does not live with its workload. A bundle emitting a ServiceMonitor needs the `monitoring` capability, and traefik is what kube-prometheus-stack reaches through `ingress`, so that edge would close a [cycle](/architecture/capability-graph.md) — the monitor sits in **`traefik-observability-config`** instead, a config bundle whose one capability is `monitoring` and which therefore sits on the far side of that edge. Its object goes in the kube-prometheus-stack namespace, the one that capability guarantees exists, and a ServiceMonitor selects across namespaces so nothing else changes. The bundle is traefik's alone — a second workload below L2 would take a second one rather than extend this. Traefik's own `metrics.prometheus.serviceMonitor` stays off and only `metrics.prometheus.service` is enabled, for the ClusterIP the monitor needs. The chart serves the exposition either way: `metrics.prometheus` is on by default on the `metrics` entrypoint, which is why `:9100` was open and unscraped for the fleet's whole life. What it yields is RED per entrypoint and per backend — `traefik_entrypoint_*` and `traefik_service_*` by `code`, `method` and `protocol` — plus `traefik_tls_certs_not_after` and `traefik_config_last_reload_success`, about 870 series per pod against a 475k head. Only `websecure` carries traffic; `addRoutersLabels` stays off, because the service labels already map onto apps and routers would be a second view of the same requests. **Traefik labels its backends `service`**, which collides with the target label carrying the Service object's name, so the scrape renames the exposed one to `exported_service` ([upstream behaviour](/reference/prometheus-metric-labels.md)); a `metricRelabelings` pair moves it to `backend` and drops the prefixed name, because `honorLabels` would resolve the collision the other way and cost a target label [the convention](/platform/telemetry-labels.md) wants.

**Loki's `monitoring.rules` is not the dashboards' dependency, it is an alert's.** `LokiRequestLatency` reads the recording rule `cluster_namespace_job_route:loki_request_duration_seconds:99quantile`, so `alerts` enabled without `rules` leaves that one alert inert — the same silence as an unselected monitor. The ServiceMonitor's 15s default interval is load-bearing for the same rules, which take a 1m rate. `multiCluster` stays off: the rules keep their `cluster_` names but aggregate by no such label, which is what [the convention](/platform/telemetry-labels.md) wants on the metrics side.

**Nothing upstream alerts on the canary.** Neither the chart nor the `loki-mixin` it is generated from references `loki_canary_*` at all — the canary ships metrics and leaves every threshold open, and its operations doc proposes none. `monitoring.additionalPrometheusRules` carries the pair worth having: `loki_canary_missing_entries_total` for loss, and `loki_canary_duplicate_entries_total` — one increment per line received more than once — which is the direct tell for the clustering-ring failure above, the one that previously showed up nowhere.

**A .NET or Go workload exposing a `/metrics` endpoint is not on its own a reason to scrape it**: the common libraries (`prometheus-net`, the runtime's own meters) instrument the host process rather than the application, so the result can be hundreds of series of GC and threadpool internals with nothing in them about what the app does. Jellyfin was measured and rejected on exactly that basis — [its own decision](/decisions/jellyfin-metrics-not-scraped.md) carries the breakdown.

**A monitor that is selected can still yield nothing, because the endpoint refuses the scrape.** controller-runtime guards its metrics port with an authn/authz filter, and volsync's chart emits a ServiceMonitor whose only endpoint config is `tlsConfig.insecureSkipVerify` — right for a cert the manager regenerates per pod start, silent about credentials — which on its own scrapes 401. Credentials cannot come from the monitor: an endpoint's `authorization` is the Safe variant, Secret references only with no `credentialsFile`, and `bearerTokenFile` is deprecated. The projected token is reachable only from `scrapeClasses` on the Prometheus CR, which a monitor opts into by name — `service-account` here, patched onto volsync's monitor by a post-renderer because the chart exposes no knob. Never give such a class `default: true`: it would hand the token to every target in the fleet. A 401 is the healthy-TLS reading, so `lastError` always tells a credential problem apart from a certificate one.

**One target is not in the cluster.** [wopr](/platform/networking-and-ingress.md) is scraped by the fleet's only `ScrapeConfig`, a static target on the hub's transit address, and it joins `job="node-exporter"` rather than taking one of its own: every mixin alert and the ZFS rule match that job exactly, and `TargetDown` groups by namespace and service, which a static target lacks — so a down wopr forms its own group instead of being diluted by the four healthy DaemonSet targets. Two costs follow. The cluster-wide rollups that join through `node_namespace_pod:kube_pod_info:` drop it correctly, but `:node_memory_MemAvailable_bytes:sum` and `cluster:node_cpu:ratio_rate5m` have no join and so count a host that is not in the cluster; neither is parameterizable from this repo. And the target carries no `namespace`, `service` or `endpoint`, which the `label-conformance` dashboard exempts by `instance` — exempting by job would take the four conformant targets with it.

**Prometheus therefore carries a `nodeSelector`.** The hub is reachable only from a node that terminates a tunnel, [mother](/platform/cluster-nyx.md) terminates none, and the Longhorn PVC attaches anywhere — so a reschedule there would stop that one scrape and nothing else. It reuses `#IngressSpoke`, which today means "has a tunnel" as well as "terminates ingress".

Grafana's **Alertmanager datasource has no backend**, so `/api/datasources/uid/alertmanager/health` answers `HTTP 500 plugin.unavailable` every time ([grafana#83794](https://github.com/grafana/grafana/issues/83794)). The datasource provisions and works in the browser; only the server-side health API is unimplemented for this type. A health sweep — `check_datasources_health` on the MCP server — therefore reports it broken on a healthy cluster. Not a fault to chase.

# Dashboards

Dashboards live with the app they describe, not with Grafana: a JSON file under the app's `files/`, turned into a ConfigMap by `#ConfigMapFiles` carrying `grafana_dashboard: "1"` plus `app.kubernetes.io/name` and `app.kubernetes.io/instance` labels. `cue/infrastructure/observability/loki/files/logs.json` is the worked example, and the exception that proves the rule: it filters every namespace by `detected_level`, so it describes Loki's contents rather than any one app and lives with Loki. A cross-signal dashboard has no such home — `label-conformance.json` reads both stores, so it sits with kube-prometheus-stack because Grafana does. Loki keeps a second, chart-rendered set beside it: `monitoring.dashboards` ships the loki-mixin, per-dashboard toggles and all, so the bloom and thanos-objstore ones are disabled for components this cluster does not run. A workload whose monitor cannot live with it keeps its dashboard beside that monitor instead, which is the third home: `traefik.json` is in `traefik-observability-config` rather than traefik's package, because `@embed` cannot leave the package directory and splitting the pair would put traefik's telemetry in two bundles for no gain.

**`traefik.json` is upstream's `contrib/grafana/traefik-kubernetes.json`, vendored and patched.** Three things had to change: `service` → `backend` everywhere including the `label_values` variable query — left alone it populates from the target label and the dropdown silently filters on the wrong thing; the export-format `__inputs`/`DS_PROMETHEUS` pair becomes an ordinary `datasource` variable, as `logs.json` has; and a local `uid` and tags. Its Apdex and two SLO panels read the `le="0.3"` and `le="1.2"` **bucket boundaries directly rather than interpolating a quantile**, which is the right use of four coarse buckets and the reason `metrics.prometheus.buckets` can be extended but never narrowed past those two. One panel, "Top slow services", divides `_sum` by `_count` with no `rate()` and so reports the mean since each process started rather than current latency; upstream's defect, carried as-is. The grafana/jsonnet-libs `traefik-mixin` was the alternative and lost on exactly that point — it has no percentile or SLO panel at all and builds both its latency views that way — plus one of its three alerts keys on `traefik_config_reloads_failure_total`, which traefik v3 does not emit.

That is not just a convention — Grafana runs with no persistence, its `storage` volume an `emptyDir`, so `grafana.db` dies with the pod. Dashboards and datasources are re-provisioned at start-up and the admin user is re-created from the `grafana-admin` Secret, but everything else held in that database — service accounts and their tokens, silences, stars, preferences — is gone. A dashboard authored in the UI is a scratch buffer, not a change, and the read-only MCP server's service account has to be re-minted by hand after every restart — Grafana provisions no service accounts ([grafana#82987](https://github.com/grafana/grafana/issues/82987)), so `kube-prometheus-stack/grafana-service-account.txt` carries the procedure.
