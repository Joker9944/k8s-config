# Deployment

**`kanidm-cluster`** serves `idm.vonarx.online` from the `security` tier. It is a `Kanidm` named `kanidm` in `kanidm-system`, deployed by the [kaniop](https://github.com/pando85/kaniop) operator (the `kanidm-operator` bundle, which provides the `kanidm` [capability](/architecture/capability-graph.md)): three `write_replica` pods, one per node by required anti-affinity, with a bundle-owned PodDisruptionBudget of `maxUnavailable: 1` since kaniop ships none. `mother`'s taint leaves exactly three nodes, so a drained node leaves one pod Pending. The volumes stay on the replicated `longhorn` class although kanidm replicates itself: on a [single-replica class](/platform/storage.md) a lost node takes the pod's data, and the empty pod that replaces it starts its own domain and needs the manual refresh below. LDAPS listens on the same Service, `kanidm:3636`, opened by `ldapPortName`. The operator renders its Ingress from `spec.ingress`, with annotations from `#IngressAnnotations`. kanidm terminates TLS itself, on a private-CA certificate covering the Service and pod names, so a `ServersTransport` trusting `nyx-ca-cert-bundle` is attached through `spec.service.annotations`. The same annotations make Traefik's load balancing sticky by cookie, because each pod holds in-flight auth and credential-update sessions in memory and signs its cookies and consent tokens with a key generated at startup; a login whose steps land on different pods fails. The CR sets uid 568 because the operator otherwise runs kanidm as root. Its log pipeline is claimed through kaniop's managed-by label, since the CR has no pod-label field — see [observability](/platform/observability.md).

Only pod 0's volume is backed up, by a standalone [`#VolsyncRestic`](/platform/backup-and-restore.md) source; restore is not wired, because kaniop never recreates its StatefulSet and Kubernetes rejects a changed claim template. kaniop writes `kanidm-admin-passwords` from `kanidmd recover-account` only while that Secret is missing, so a restored pod 0 leaves it holding passwords the database does not, and every kaniop login fails; deleting the Secret makes kaniop recover both accounts again. kaniop's own backup is not used: its CRDs are `v1alpha1`, online upload is experimental for want of a completion marker from kanidm, and its restore cannot read 1.12 dumps — the data mover finds the domain entry by `uuid.UU`/`domain_name.N8`, where 1.12 writes `US`/`N8S`.

kaniop v0.22.1 builds against the kanidm 1.11 client SDK and marks 1.12 servers incompatible ([#1141](https://github.com/pando85/kaniop/issues/1141)), so `disableUpgradeChecks` is set. It gates only the upgrade path. Renovate holds `kanidm/server` until kaniop catches up. The kanidm image has no shell or `tar`, so files go in and out through an ephemeral container, and `kanidmd database backup` is offline-only and still wants the TLS paths set.

# Replication

kaniop meshes every pod of the CR with mutual-pull on port 8444 and advertises `repl://<pod>.<name>.<ns>.svc.cluster.local:8444`. `primaryNode` is unset, so no pod has `automatic_refresh`: replication runs, but a pod whose domain diverges, such as a new or emptied one, stays split until it is refreshed. To recover, set `primaryNode` on the CR until the others have refreshed from pod 0, then clear it. Leaving it set would let an empty pod 0 replace everyone's data with its own. Its admission policy allows one primary only, across replica groups and external nodes.

kanidm 1.12.0 mints replication certificates whose issuer carries `O=Kanidm Replication` while the subject does not, so the rustls pin rejects them (`UnknownIssuer`/`UnknownCA`; [kanidm#4709](https://github.com/kanidm/kanidm/issues/4709)). 1.12.1 fixes new ones; a certificate minted earlier needs `kanidmd renew-replication-certificate`.

# Client registration

opencloud alone ships a `kanidm-oidc.txt` beside its package, holding the verbatim `kanidm` CLI commands to create the OAuth2 client, add redirect URLs, create the app's groups and set scope maps; the group model they plug into is the [IDM layout](/platform/kanidm-idm-layout.md). What a granted scope actually puts in the token is [claim mapping](/reference/oidc-claim-mapping.md). Every client that authorises by group grants the legacy `groups` scope, whose values are SPNs, so a consumer's role configuration spells its groups `<app>_admins@idm.vonarx.online` — `groups_name` is the lever for one that cannot take the suffix. gotify's client also registers the Android app's `gotify://oidc/callback`: kanidm files a non-`http(s)` redirect as an _opaque origin_ and matches it on a confidential client too, where the book reads as if custom schemes were public-client only. opencloud is the only entry that is **public** rather than confidential — its web UI is a browser SPA whose chart carries no client-secret setting — and the only one whose single client serves four apps: kanidm's issuer URL and token signing keys are per client while OpenCloud validates against one `OC_OIDC_ISSUER`, so a client per app yields tokens the proxy rejects. Web, desktop, Android and iOS all authenticate as `openclouddesktop`, put there by OpenCloud's own webfinger service, which hands each platform a `client_id` in place of the vendor-fixed one it ships with. Its desktop app needs `enable-localhost-redirects` for the ephemeral port it listens on. Its authorisation is driven by a claim map, as Grafana's role is: the proxy reads a `roles` claim and matches `opencloudAdmin`/`opencloudUser`, so the scope map has to grant `roles` as well.

**Nothing in the repo applies it**: reconcile the manifests, then replay the file by hand against a running kanidm. Its client is public and has no secret, but the file carries a second manual step: it is kanidm's only LDAP consumer, reading users and groups over LDAPS (read-only, `dn=token` binding with a service-account api token), and that token is what goes into its [SOPS secret](/workflows/secrets-sops.md).

**Every other client is provisioned by kaniop** — audiobookshelf, gotify, grafana, jellyfin, komga and the four servarr apps. Their groups and OAuth2 clients are `#KanidmGroup` and `#KanidmOAuth2Client` CRs in the app's own package, referencing the cluster through `#KanidmRef`; kaniop reconciles them only in namespaces carrying `#KanidmProvisioningLabel`, which the `Kanidm` CR's namespace selectors match. A CR adopts an existing entry of the same name in place, and deleting the CR deletes the entry. `#KanidmGroup` carries Flux's `prune: disabled`, so dropping a group from git leaves the CR and the group in place; deleting its namespace still removes both. `members` is an exact list, so `#KanidmGroup` declares an app group with its tier group as sole member and the tier groups, which hold the people, stay undeclared. kaniop reads a confidential client's existing secret rather than rotating it and writes it to `<client>-kanidm-oauth2-credentials` as `CLIENT_ID` and `CLIENT_SECRET`. audiobookshelf and jellyfin keep their own copy of the secret, entered in their settings, so theirs is unread; the others map those keys onto their own variables with `secretKeyRef`: `envFrom` would also expose them under the generic names, and `secretKeyAliases` only adds keys beside the canonical two. **Sonarr and Radarr sign in natively and admit one user.** Upstream allows no more, so that trackers cannot read multi-user support as account sharing ([Sonarr#1682](https://github.com/Sonarr/Sonarr/issues/1682)). `OidcUserIdentifier` matches only a verified `email` or `sub`, never an SPN, so it holds the owner's UUID, kept in SOPS as `servarr-oidc-user`. ASP.NET honours `X-Forwarded-Proto` only from `TrustedNetworks`; left empty, the redirect URI goes out as `http://` and kanidm's strict match rejects it. Prowlarr has no native OIDC and stays behind the plugin, reading its client secret from kaniop's Secret. Service accounts are not provisioned this way: kaniop compares `entry_managed_by` by name, kanidm 1.12 returns it unresolved, and the reconcile re-patches the account forever ([pando85/kaniop#1127](https://github.com/pando85/kaniop/issues/1127)).

Apps with no OIDC support of their own are fronted by Traefik's `oidc` plugin instead; see [ingress](/platform/networking-and-ingress.md).
