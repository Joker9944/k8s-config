# Deployment

Two instances of one database replicate with each other in the `security` tier.

**`kanidm-cluster`** serves `idm.vonarx.online`. It is a `Kanidm` named `kanidm` in `kanidm-system`, deployed by the [kaniop](https://github.com/pando85/kaniop) operator (the `kanidm-operator` bundle, which provides the `kanidm` [capability](/architecture/capability-graph.md)): one `write_replica`, primary for replication. LDAPS listens on the same Service, `kanidm:3636`, opened by `ldapPortName`. The operator renders its Ingress from `spec.ingress`, with annotations from `#IngressAnnotations`. kanidm terminates TLS itself, on a private-CA certificate covering the Service and pod names, so a `ServersTransport` trusting `nyx-ca-cert-bundle` is attached through `spec.service.annotations`. The CR sets the app-template uid because the operator otherwise runs kanidm as root. Only the primary's volume is backed up, by a standalone [`#VolsyncRestic`](/platform/backup-and-restore.md) source; restore is not wired, because kaniop never recreates its StatefulSet and Kubernetes rejects a changed claim template. kaniop's own backup is not used: its CRDs are `v1alpha1`, online upload is experimental for want of a completion marker from kanidm, and its restore cannot read 1.12 dumps.

**`kanidm`** is the app-template StatefulSet in `kanidm`. It serves no clients and has no ingress; it still exposes LDAPS on `kanidm-ldaps:636`. Its certificate comes from [`#NamespaceCert`](/architecture/cue-layout.md). `KANIDM_TRUST_X_FORWARD_FOR: true` makes rate limiting and audit logs see real client addresses. Health probes exec `kanidmd scripting healthcheck`.

# Replication

Mutual-pull on port 8444. The new cluster is the primary, and the app-template instance has `automatic_refresh`, so a diverged secondary is wiped from the primary and never the reverse.

- **New → old certificate.** kaniop keeps each pod's replication certificate in `<pod>-cert` (`tls.der.b64url`). Reflector mirrors `kanidm-default-0-cert` into `kanidm`. kanidm accepts a partner certificate only inline, so an init container fills the `@PARTNER_CERT@` placeholder in `files/server.toml` from the mirror, and reloader rolls the pod when the mirror changes. The source's `reflection-allowed` annotations are set by hand, because kaniop has no field for them. They survive the operator's updates and are lost if it recreates the Secret, and then replication stops without an error.
- **Old → new certificate.** The SOPS Secret `kanidm-legacy-replication-cert` pins it. It changes only on a manual `kanidmd renew-replication-certificate`.
- **Origins.** kaniop advertises `repl://<pod>.<name>.<ns>.svc.cluster.local:8444` and renders `externalReplicationNodes` into `/run/kanidm/server.toml` with an init container. Its admission policy allows one primary only: either a replica group with `primaryNode` or an external node with `automaticRefresh`.
- **1.12.0 certificates are unusable.** kanidm 1.12.0 mints replication certificates whose issuer carries `O=Kanidm Replication` while the subject does not, so the rustls pin rejects them (`UnknownIssuer`/`UnknownCA`; [kanidm#4709](https://github.com/kanidm/kanidm/issues/4709)). 1.12.1 fixes new ones, and a certificate minted earlier needs a renew.

kaniop v0.22.1 builds against the kanidm 1.11 client SDK and marks 1.12 servers incompatible ([#1141](https://github.com/pando85/kaniop/issues/1141)), so `disableUpgradeChecks` is set. It gates only the upgrade path; backup rendering does not depend on it. Its restore path cannot read a 1.12 backup either: the data mover finds the domain entry by `uuid.UU`/`domain_name.N8`, where 1.12 writes `US`/`N8S`. Neither the kanidm image nor `kanidmd database backup` is convenient to work with: the image has no shell or `tar`, so files go in and out through an ephemeral container, and the backup is offline-only and still wants the TLS paths set.

# Client registration is manual

Ten workloads ship a `kanidm-oidc.txt` beside their package: audiobookshelf, gotify, jellyfin, komga, opencloud and kube-prometheus-stack (for Grafana) at the package root, and the four servarr apps — prowlarr, radarr-standard, sonarr-anime, sonarr-standard — under `servarr/kanidm-oidc/<app>.txt`, because that package is flat. Each holds the verbatim `kanidm` CLI commands to create the OAuth2 client, add redirect URLs, create `<app>_admins`/`<app>_users` groups, add a shared tier group as a _member_ of each (`media_*`, `cloud_*` or `monitoring_*`, matching the app's Flux tier), and set scope maps. What a granted scope actually puts in the token is [claim mapping](/reference/oidc-claim-mapping.md). Every client here grants the legacy `groups` scope, whose values are SPNs, so a consumer's role configuration spells its groups `<app>_admins@idm.vonarx.online` — `groups_name` is the lever for one that cannot take the suffix. Membership therefore flows tier group → app group; the tier groups themselves are created out-of-band. gotify's file also registers the Android app's `gotify://oidc/callback`: kanidm files a non-`http(s)` redirect as an _opaque origin_ and matches it on a confidential client too, where the book reads as if custom schemes were public-client only. opencloud is the only entry that is **public** rather than confidential — its web UI is a browser SPA whose chart carries no client-secret setting — and the only one whose single client serves four apps: kanidm's issuer URL and token signing keys are per client while OpenCloud validates against one `OC_OIDC_ISSUER`, so a client per app yields tokens the proxy rejects. Web, desktop, Android and iOS all authenticate as `openclouddesktop`, put there by OpenCloud's own webfinger service, which hands each platform a `client_id` in place of the vendor-fixed one it ships with. Its desktop app needs `enable-localhost-redirects` for the ephemeral port it listens on. It is also the only one whose authorisation is driven by a claim map: the proxy reads a `roles` claim and matches `opencloudAdmin`/`opencloudUser`, so the scope map has to grant `roles` as well.

**Nothing in the repo applies them.** No package reads them, and kanidm has no declarative client CRD here. Deploying an app with SSO therefore takes two steps: reconcile the manifests, then replay the file by hand against a running kanidm. The client secret then has to be put into the app's [SOPS secret](/workflows/secrets-sops.md) separately — the file does not record where it goes. A public client has none, but opencloud's file carries a second manual step: it is kanidm's only LDAP consumer, reading users and groups over LDAPS (read-only, `dn=token` binding with a service-account api token), and that token is what goes into its [SOPS secret](/workflows/secrets-sops.md).

Apps with no OIDC support of their own are fronted by Traefik's `oidc` plugin instead; see [ingress](/platform/networking-and-ingress.md).
